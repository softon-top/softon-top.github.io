上周技术圈被一张图刷屏：一台折叠屏 iPhone，展开就是完整的 Windows 11 桌面，Edge 在跑，Antigravity 在跑，扬声器出声，麦克风能收。不是远程桌面，不是云电脑串流，是本地。

更让人想点进去的是作者那句话——谷歌 AI Studio 负责人 Ammaar Reshi 说，他用 Gemini 4 Carbon 加上多 Agent 协作，大约两小时就做出来了。

两小时。这三个字是诱饵，也是这篇文章要拆的坑。因为把官方 README 读完，你会发现真正的工程量根本不在那两小时里，而在于它必须同时满足 Windows NT 内核、ARMv8 架构、PCIe/USB/声卡硬件、iOS TXM 内存模型这四套互相打架的约束。少任何一条，Windows 就停在开机 Logo。

TL;DR

  • WindowsiOS 跑的是未修改的零售版 Windows 11 24H2 ARM64（Build 26100），在免越狱的 iPhone Duo（iPhone19,4，A20 Pro，iOS 27 TXM）上，不依赖 Hypervisor.framework。
  • 免越狱的前提下，硬件 EL2 虚拟化在 iOS 16.4+ 已被苹果封死；UTM SE 这类解释器模拟器又慢 5–10 倍，带不动 Chromium/Electron 多进程栈。所以只剩一条路：ARM64→ARM64 动态二进制翻译 + 4KB 软件 MMU。
  • 最硬的三处：Windows 把 ASID 放在 TTBR1_EL1（TCR_EL1.A1=1）且每次上下文切换会瞬态经过 ASID 0；Prism 的 LDAPUR/STLUR 非对齐访问在苹果 EL0 会直接 SIGBUS；virtio-win 没有 Windows 声卡驱动，得从零写一个 Intel ICH6 HDA 控制器。
  • 结果是 idle 内存 1.46 GB / 4.5 GB（约 31.7%），4 个 A20 Pro 性能核 89% WFI 空闲，Edge 能渲染 HTTPS 页面，Google/passkey OAuth 能走通。
  • 门槛：Apple Silicon Mac + Xcode + xcodegen/meson/ninja/llvm + 官方 Win11 ARM64 ESD + EDK2 QEMU_EFI.fd + WHQL NetKVM 驱动。实验性项目，别指望日常可用。

为什么这事此前没人做成？

先把「不可能」这三个字拆开。不是没人试过，是三条路都被堵了。

第一条：硬件虚拟化。 苹果从 iOS 16.4 起限制 com.apple.developer.kernel.hypervisor，也就是 Hypervisor.framework。非越狱的 iPhone 上，硬件 EL2 虚拟化（UTM HV 那条路）没了。到 iOS 26/27 的 A20 Pro 这代，**Trusted Execution Monitor（TXM）**又加了一层：对任意 MAP_JIT 执行做硬件页表签名校验。你想在用户态划一块内存出来当"虚拟 CPU 的 RAM"，硬件先问一句：签名呢？

第二条：解释器模拟。 UTM SE 这类 sideload / App Store 模拟器，落到 QEMU 的 TCG 线程解释器（TCI）。解释执行下，Windows 11 24H2 走到桌面要几十分钟，更别提驱动 Edge、Antigravity 这种多进程 Chromium/Electron 栈。慢 5–10 倍不是优化问题，是路线问题。

第三条：ARM64 二进制翻译只伺候过 macOS / Linux，没伺候过 Windows NT。 Leviidev/Henge 已经证明：EL1&0 的 ARM64→ARM64 动态翻译器 + 软件 MMU + TXM 双映射 JIT，能让 macOS（vmapple，16KB 页）在 modern iPhone 上接近原生速度跑起来。但 Windows NT ARM64 内核要的东西，Henge 没凑齐：

  • 严格 4KB stage-1 翻译粒度（TG0/TG1），跑在 16KB 页的 Darwin host 上；
  • Windows 的 TCR_EL1.A1 = 1，ASID 放在 TTBR1_EL1[63:48]，而且 KiSwapProcess 里会有瞬态 ASID 0；
  • Windows 11 的 Prism（xtajit64.dll） 非对齐 FEAT_LRCPC2（LDAPUR/STLUR）内存序语义（SCTLR_EL1.nAA = 1）；
  • 一整套能塞进 iOS Jetsam 内存预算的 UEFI + ACPI 6.3 + GICv3 LPI/ITS MSI-X + PCIe NVMe + USB 3.0 xHCI + Intel ICH6 HD Audio + WHQL VirtIO-Net PC 平台。

WindowsiOS 干的事，就是把这四条凑齐。下面按"哪条最难"排序拆。

ASID 放错位置：Windows 唯一一处让 TLB 缓存全废的设计

这是整篇技术含量最高的一段，也是 README 里写得最较真的地方。

Linux 和 macOS 都把用户 ASID 放在 TTBR0_EL1[63:48]。Windows 11 ARM64 不——它把 TCR_EL1.A1（bit 22）设为 1，ASID 挪到 TTBR1_EL1[63:48]。这本身只是"放的位置不一样"，但真正的坑在下一步：每次进程切换（KiSwapProcess），Windows 会写新的 TTBR0_EL1（DirectoryTableBase），而 TTBR1_EL1 里的 ASID 会瞬态经过 ASID 0。

桌面上跑起来，这个切换是 64,800+ 次/秒。

为什么这是灾难？因为软件 MMU 通常按 TTBR0 做 TLB 键，或者干脆在 ASID 0 下做 stash。两种做法都死：

  • 按 TTBR0 键 → 每次上下文切换，所有用户 TLB 项全部抖动失效；
  • 在 ASID 0 下 stash → 物理 DirectoryTableBase 页被回收复用时，陈旧的用户映射跨进程泄漏。

解法在 core/mmu.c 的 hv_mmu_ukey()：合成一个规范地址空间键 (ASID << 48) | (TTBR0 & OA_MASK)，当 TCR.A1 == 1 时从 TTBR1 读 ASID，遇到 ASID == 0 直接返回 0。HvTlbStash（hv_tlb_switch_user）在上下文切换时保存/恢复约 266–313 个活跃用户 TLB 槽，微秒级完成，不用重走四级页表。

顺带一提，core/sysreg.c 还得伪造 CPU 身份：暴露 ARM Cortex-A76 r4p1 的 MIDR_EL1（0x414fd0b1）、校准过的 PMCCNTR_EL0，以及按特权级分的 4 路软件 TLB（[EL0, EL1, EL1+PAN] 打包进单条 128 字节 cache line，这样内核在用户拷贝前后切 PAN 不会把 TLB 状态刷掉）。ntoskrnl.exe 在 KiInitializeKernel 里会校验 CPU 标识和周期计数器——糊弄不过去。

一个 rt == 31 引发的死锁

Clang 编出来的 C++（Chromium 的 msedge.dll、Electron 的 Antigravity.exe）经常发射这么一对：

ldxr xzr, [rn]
stlxr ws, xt, [rn]

用意是"布个独占监视器，但我不关心旧值"，所以源寄存器写 xzr（rt == 31）。

问题在于 AArch64 的机器码里，31 这个编号在 LDXR 中编码 XZR，但在 MOV/ADD 里编码 SP。如果你的翻译器在检查 rt != 31 之前，没把真实的内存字写进独占值字段 HV_CPU_EXCL_VAL，那么：要么 guest 的 SP 被改写，要么当 [rn] != 0 时 STLXR 的 CASAL 比较永远失败——渲染线程直接死锁。

translate_excl() 的处理：永远先载入 scratch 寄存器 x6，把 x6 记进 HV_CPU_EXCL_VAL，rt == 31 时抑制回写。128 位 SLIST（LDXP/STXP → LDP + CASPAL）也走同一条 inline LSE 快路径——Windows 的 dispatcher、heap、I/O manager 每秒要跑几百万次无锁 ExpInterlockedPopEntrySList，每次独占对都退出到 C 是扛不住启动性能的。

Prism 的非对齐访问，会被苹果SIGBUS掉

Windows 11 ARM64 的 Prism（xtajit64.dll）负责把 x86-64 翻成 ARM64。它运行时 SCTLR_EL1.nAA = 1，允许 Weakly-Ordered RCpc 指令做非对齐访问，于是会发射非对齐的 LDAPUR / STLUR / LDAPR（FEAT_LRCPC / FEAT_LRCPC2）来模拟 x86-64 的 TSO 内存序。

而 Darwin/XNU 在苹果芯片的 EL0 用户态强制 SCTLR_EL1.nAA = 0。结果就是：在 host 上一个非对齐的 LDAPUR/STLUR，直接 SIGBUS（EXC_ARM_DA_ALIGN）把进程干掉。

translate_mem_impl() 的做法是在 HV_MEM_ORDERED 访问上套一层 inline 对齐掩码（host_align）：对齐的 RCpc 指令剥掉 imm9 后一条指令内联执行；非对齐的则无缝跳到 core/memop.c 里的 acquire/release 栅栏软件辅助例程。

没有现成驱动，就自己造一个声卡

这是我觉得最"暴力"的一处。

Red Hat 的 virtio-win 套件里没有 Windows 的 virtio-snd 驱动。也就是说，如果你按常规 virtio 思路接音频，Windows 11 ARM64 里就是没声音。

WindowsiOS 的选择是：从零写一个 Intel ICH6 High Definition Audio PCIe 控制器（8086:2668，PCI\CC_0403），配一个 6 节点全双工 HDA Codec（1af4:0022）：

  • NID 0 Root → NID 1 Audio Function Group → NID 2 立体声 DAC + NID 3 扬声器 Pin Complex（0x01114010）+ NID 4 立体声 ADC + NID 5 麦克风 Pin Complex（0x01a19020）；
  • 完整 CORB/RIRB verb 环引擎、24.000 MHz WALCLK、DMA Position Buffer（DPLBASE/DPUBASE）、LPIB、scatter-gather BDL 流。

效果是 Windows 11 首次开机自动绑上 inbox 的 hdaudbus.sys + HdAudio.sys，48 kHz S16LE 播放流到 iOS RemoteIO（AudioUnit），麦克风采集走 AudioQueueNewInput。零驱动安装，插上就响。

同类的"从零造"还有整台 PC 平台：EDK2 ArmVirtQemu UEFI（双 64MB pflash，pflash1 是可持久 Intel CFI01 NVRAM，这样 bcdboot 的 Boot0001 能跨重启存活）、程序化 ACPI 6.3（RSDP/XSDT/FADT/GTDT/MCFG/MADT/IORT/DSDT）、GICv3 ITS、NVMe 1.4（序列号 WIN11IOS01，带 deferred flush，避免 NTFS 元数据突发卡住 iOS 闪存）、USB 3.0 xHCI（实现了 Windows USBXHCI.SYS 硬性要求的 Event Data TRB 累积传输长度 EDTLA 与 CC_STALL 端点 halt 恢复）。

384 MiB JIT 与 4.5 GB 内存：跟 iOS 内存模型讨价还价

iOS 26/27 TXM 设备上，放在 0x7000000000 以上的可执行 JIT 映射会硬件挂死。winios_jit.c 的做法是：在 Mach-O 加载期于 __DATA 里 0x180000000 以下静态保留一块零填充区，在 debugserver 分配 _M<size>,rx 之前释放它，抢出 384 MiB 的 RX/RW 双映射 JIT。

内存方面，在 CS_DEBUGGED 激活期间用 mach_make_memory_entry_64 + mach_memory_entry_ownership(..., LEDGER_NO_FOOTPRINT) 预分配 4,608 MiB（4.5 GB）Jetsam 豁免的客户机内存，然后 LLDB 干净退出——给 iOS 留 约 2–3 GB Jetsam 余量。

再配合"离线 Hive 手术"：用 WinPE 环境加一个 freestanding ARM64 Win32 工具（tools/opt_hive_arm64.c，以 SeBackupPrivilege + SeRestorePrivilege + REG_OPTION_BACKUP_RESTORE 打开 SYSTEM/SOFTWARE hive，绕过 TrustedInstaller DACL），optimize_windows_lite.py 砍掉 35+ 个后台 UWP/遥测/Defender/indexer 和 KVA Shadow 开销。最终：

指标 数值
空闲桌面内存 1.46 GB / 4.5 GB（~31.7%）
4 核 WFI 空闲率 89%
Guest RAM 4,608 MiB（Jetsam 豁免）
JIT 映射 384 MiB RX/RW 双映射（< 0x7000000000）
iOS Jetsam 余量 ~2–3 GB
镜像容器 hvsparse（跳过零块）

内存地图：4.5 GB 客户机 RAM 和 384 MiB JIT 怎么摆

把上面的内存策略落成一张表，读者能更直观看到"为什么一定要跟 iOS 讨价还价"。以下是 README 给出的客户机物理地址映射与 PCIe 拓扑：

客户机物理地址 大小 设备 / 子系统
0x0000_0000 64 MiB pflash0 — EDK2 ArmVirtQemu UEFI 代码（只读 HvRam）
0x0400_0000 64 MiB pflash1 — 可持久 Intel CFI01 UEFI 变量存储（vars.fd）
0x0800_0000 64 KiB ARM GICv3 Distributor（GICD）
0x0808_0000 128 KiB ARM GICv3 Interrupt Translation Service（GIC ITS#0，LPI MSI-X）
0x080A_0000 15 MiB ARM GICv3 每 vCPU Redistributor（GICR）
0x1000_0000 752 MiB PCIe 32 位 MMIO 窗口 + PIO
0x4000_0000 4.5 GiB 客户机系统 DRAM（iOS 上 hv_alloc_no_footprint）
0x40_1000_0000 256 MiB PCIe ECAM 配置空间（MCFG）
0x80_0000_0000 512 GiB PCIe 64 位高位 MMIO BAR 窗口

PCIe GPEX 总线 00 上的五个端点，就是前面几节反复提到的那些"从零造"的硬件：

  • 00:00.0 — Red Hat GPEX 宿主桥（1b36:0008）
  • 00:01.0 — VirtIO 网卡（1af4:1000，WHQL NetKVM + libslirp NAT + /.henge/ WebDAV/OAuth）
  • 00:02.0 — NVMe 1.4 控制器（1b36:0010，序列号 WIN11IOS01，MSI-X + hvsparse 后备）
  • 00:03.0 — USB 3.0 xHCI 控制器（1b36:000d，Port 1 HID Boot 键盘 + Port 2 绝对定位平板）
  • 00:04.0 — Intel ICH6 HD Audio（8086:2668，Codec 1af4:0022，立体声喇叭 + 立体声麦克风）

看这张表就能明白一件反直觉的事：这不是一台"手机模拟 PC"，是一台"PC 塞进手机"。所有标准 PC 固件/中断/存储/USB/音频/网络组件一个不少，只是全都用软件实现，跑在 iOS 用户态。Windows 11 24H2 拒绍 FDT/DeviceTree 启动，只认 ServerReady/PC 级的 UEFI + ACPI + MSI-X 拓扑——所以这层"造假"不是炫技，是硬需求。

装机链路：照着走一遍

先说前置条件，这部分能劝退绝大多数人：

  • Apple Silicon Mac（M1 或更新；作者开发用 M5 Pro）；
  • Xcode、xcodegen、meson、ninja、pkg-config、libslirp、llvm/lld（编 freestanding AArch64 Win32 客户机辅助工具用）、Python 3；
  • 官方 Windows 11 24H2 ARM64 零售 ESD，放在 work/downloads/Win11_24H2_ARM64_en-us.esd；
  • EDK2 QEMU_EFI.fd 放 work/code.fd；
  • WHQL virtio-win 的 NetKVM（w11/ARM64）驱动。

注意：git 里不放任何镜像、固件、ISO，全在 work/ 和 build/，被 .gitignore 强制排除。

# 1. 交叉编译 iOS 依赖（libffi + glib + libslirp，目标 arm64-apple-ios）
./scripts/build_ios_deps.sh

# 2. 构建 macOS 宿主 VM、稀疏打包器、iOS 静态库，并跑核心 JIT/MMU 单测
make -j8 all ios-lib test-core

# 3. 无人值守 WinPE DISM + NetKVM 注入 + BCDBOOT UEFI NVRAM 配置
/opt/homebrew/bin/python3 scripts/provision_windows_arm64.py

# 4. 离线 WinPE DISM 去臃肿 + SeRestorePrivilege 注册表 hive 手术 -> 1.46 GB 空闲
/opt/homebrew/bin/python3 scripts/optimize_windows_lite.py

# 5. 打成跳过零块的稀疏容器，方便往 iOS 传
./build/hvsparse pack work/windows11_lite.img work/windows11.hvsparse

想先在 macOS 上验证一遍（不碰 iPhone）：

HV_OAUTH_BRIDGE=1 ./build/winvm \
  --cpus 4 --ram 4608 \
  --bios work/code.fd --vars work/vars.fd \
  --disk work/windows11_lite.img

真机部署：

# 由 ios/project.yml 生成 Xcode 工程并构建 Release iphoneos bundle
xcodegen generate --spec ios/project.yml
xcodebuild -project ios/WindowsiOS.xcodeproj -scheme WindowsiOS -configuration Release \
  -sdk iphoneos -derivedDataPath build/DerivedData build

# 装 app，把 windows11.hvsparse + code.fd + vars.fd 拷到 Documents/Machines/Win11
xcrun devicectl device install app --device <DEVICE_UDID> \
  build/DerivedData/Build/Products/Release-iphoneos/WindowsiOS.app

# 以 --start-stopped 启动，用 LLDB bless 384 MiB TXM JIT + 4,608 MiB ledger-exempt RAM，再干净 detach
./scripts/launch_on_duo.sh <DEVICE_UDID> me.ammaar.windowsios

这里有个值得说的模式：每个上游解决一个特定子问题，WindowsiOS 只解决"把它们同时跑在 NT 内核下"这个组合问题。 Henge 伺候 macOS，LinuxRunner 伺候 Linux，StikDebug 解决 iOS 上的调试附着与页 bless，libslirp 解决网络，EDK2 解决固件，virtio-win 解决网卡——但没有任何一个同时满足 NT 内核的 4KB 页 + TCR_EL1.A1 ASID + Prism LRCPC2 + 完整 PC 平台。这正是 README 里 “What Didn’t Exist Before This” 那一节的真正含义。

许可证上也得留神：主体是 GPL-2.0-or-later，但混了 MPL-2.0（StikDebug）、BSD-3-Clause（libslirp、virtio-win）、MIT（idevice）、BSD-2-Clause-Patent（EDK2）。你要拿它做二次分发，得按 THIRD_PARTY_NOTICES.md 逐条对上。

交互：把折叠屏用成一台笔记本

硬件跑起来之后是体验层。WindowsiOS 钩了 iOS 27 的 UIHingeInteraction，两种姿态：

  • 折叠 = 笔记本模式：上半屏是 Windows（Obsidian-Glass 金属质感，Studio 摄像头指示灯，XAML 双击吸附），下半屏是 Midnight-Sapphire CNC 键盘面板——6 行 chiclet 键（F1–F10、Copilot 键、上下箭头叠放）+ 120 Hz 触觉哑光玻璃多点触控板。
  • 展开 = Open Studio 模式：边缘到边缘的完整 Windows 11 画布，自动隐藏的磨砂命令胶囊。

还有一个很聪明的细节：OAuth 回环。在 Antigravity 这类桌面 IDE 里点"Continue with Google"，redirect_uri 指向 Windows 内的一个 http://localhost:<PORT>/oauth-callback。WinIOSBrowser.exe（14 KB freestanding AArch64 Win32，注册为默认 HTTP/HTTPS handler）会解析这个 localhost URI，起一条客户机 TCP 中继（QEMU 用户态 NAT 的客户机侧地址 ↔ 本机回环地址，端口不变），调 PUT /.henge/expose-port 让 host 的 net_slirp.c 把 iOS 侧的本机回环和 IPv6 回环转发进客户机，再调 /.henge/open-url 弹出 iOS 原生 SFSafariViewController——直接复用你已有的 Safari Google 会话、Passkey、Face ID。token 一落回 Windows，sheet 带触感反馈自动收起。

常见问题

Q1: 免越狱为什么这么难？苹果到底封了什么？

A: 从 iOS 16.4 起，苹果限制了 com.apple.developer.kernel.hypervisor 权限，非越狱设备上拿不到 Hypervisor.framework，硬件 EL2 虚拟化（UTM HV 那条路）直接没了。到 iOS 26/27 的 A20 Pro，TXM 还会对任意 MAP_JIT 执行做硬件页表签名校验，用户态自己划内存当虚拟 RAM 也会被拦。

Q2: 它和 UTM 的区别到底在哪？

A: UTM SE 走 QEMU 的 TCG 解释器，Windows 11 24H2 走到桌面要几十分钟，且带不动 Chromium/Electron 多进程栈。WindowsiOS 走 ARM64→ARM64 动态二进制翻译 + 4KB 软件 MMU，配合 TXM 双映射 JIT，速度接近原生，能跑 Edge 和 Antigravity。

Q3: TCR_EL1.A1 = 1 是什么？为什么它差点搞死整个项目？

A: 这是 Windows ARM64 把进程 ASID 放在 TTBR1_EL1[63:48]（而非 Linux/macOS 的 TTBR0_EL1[63:48]）的开关。配合 KiSwapProcess 每次切换瞬态经过 ASID 0（桌面负载下 64,800+ 次/秒），按 TTBR0 键或按 ASID 0 stash 都会让 TLB 全废或跨进程泄漏。解法是 hv_mmu_ukey() 从 TTBR1 读 ASID 并显式处理 0。

Q4: Prism 的非对齐访问为什么会 SIGBUS？

A: Windows 11 ARM64 的 Prism（xtajit64.dll）在 SCTLR_EL1.nAA = 1 下会发非对齐 LDAPUR/STLUR，而苹果 EL0 强制 nAA = 0，host 上非对齐执行直接 EXC_ARM_DA_ALIGN。翻译器对 HV_MEM_ORDERED 访问加 inline 对齐掩码，非对齐的落到带栅栏的软件辅助例程。

Q5: 我没 Apple Silicon Mac，能玩吗？

A: 不能。前置条件硬性要求 Apple Silicon Mac + Xcode，镜像制备（ESD → DISM → hive 手术 → hvsparse）全在 macOS 上完成。作者开发用 M5 Pro。

Q6: 这项目是"2 小时"搞出来的吗？

A: 作者 Ammaar Reshi 说的是用 Gemini 4 Carbon 加多 Agent 协作，约 2 小时完成开发。但 README 里"原创且困难"的部分——4KB 软件 MMU、LSE 原子、LRCPC2 仿真、整台虚拟 PC 平台、ICH6 声卡、TXM JIT 与 hive 手术——是实打实的内核与硬件工程，且大量建立在 Henge、Husk、LinuxRunner、StikDebug、libslirp、EDK2、virtio-win 的既有成果上。2 小时是"组装 + 攻关"的时间，不是"从零发明"的时间。

Q7: 现在能当日常系统用吗？

A: 不能。官方 README 明确写"实验性项目"。它验证的是技术可行性：未修改的零售版 Windows 11 24H2 ARM64，在免越狱 iOS 上跑到可用交互。别把它当生产力环境。

Cosh：一个 Rust 写的 Agent 编排层，想同时跑 Claude、Codex、Goose 进同一个终端

终端里同时开三个 Agent，各自跑在独立分支上，主 Agent 只负责派活和收报告——这个画面在 2024 年还像科幻，2026 年 11 月已经有一个开源项目把它做成了单 binary。

它叫 Cosh（仓库 DiegoZaluski/co-sh），Rust 写的通用编码 Agent，主打的不是“替代 Claude Code”，而是“把一堆现成 Agent 塞进同一个 TUI 里一起跑”。项目 2026-06-01 建仓，10 月 1 日发 v0.1.0，11 月 10 日已到 v0.2.2，迭代速度几乎是几天一个版本。

TL;DR

  • Cosh 的自我定位是编排层（orchestration layer），不替换 Claude Code / Codex / Goose，而是让它们并排跑在同一个终端里。
  • 核心机制：/agents 分屏 + 每个 Agent 独立会话/模型/可选 git worktree + 主 Agent 通过 agents_call / agents_compact 派活。
  • 接入外部 Agent 靠 ACP（Agent Client Protocol），注册表内置 Gemini、Claude、Codex、Cline、Devin、Goose、OpenCode、Kilo，也允许用户自定义。
  • 和 Claude Squad、Agent Orchestrator 的差别：Cosh 更偏“个人开发者的终端工作台”，Squad 偏单 Agent 并行会话，Orchestrator 偏团队协作流。
  • 它真正的工程价值不在 UI，而在运行时：worktree 隔离、会话持久化、上下文压缩、自然停机门禁、bash 进程树看门狗。
  • 目前 macOS 官方标注“尚未测试”，Linux/Windows 已测；Stars 数（13）还很低，属于早期项目。

它到底想解决什么：一个终端里的“Agent 团队”

先别急着看功能表。Cosh 的 README 第一句话就划清了界限：

co-sh isn’t meant to replace established coding agents — it’s designed to work alongside them as an orchestration layer.

这句话很关键。它没有说“我比 Claude Code 更强”，而是说“我不跟你抢方向盘，我帮你把多个司机安排进同一辆车的不同座位”。

具体到交互层，它的主卖点是 /agents 模式：你按 /agents 打开一个多选面板，勾选想跑的外部 Agent（Gemini、Claude、Codex、Cline……），聊天区就被切成多个窗格。每个窗格是一个独立 Agent，保留自己的会话、模型，还可以挂自己的 git worktree。你输入一句 prompt，它会同时扇出给所有选中的 Agent；主 Agent 负责派任务、收报告、协调上下文。

# 启动（官方安装脚本）
curl -fsSL https://raw.githubusercontent.com/DiegoZaluski/co-sh/main/download.sh | bash

# Windows PowerShell
irm https://raw.githubusercontent.com/DiegoZaluski/co-sh/main/download.ps1 | iex

# 安装后
cosh

可选环境变量有三个：COSH_BIN_DIR（安装目录）、COSH_VERSION（锁版本）、COSH_VARIANT（默认 slim，或 slim-embed 带本地 RAG，走 fastembed）。

这不是“多开几个终端窗口”的升级版吗？是，但差别在共享工作区 + 统一调度。每个窗格能看到兄弟 Agent 的存在（官方叫 peer preamble），主 Agent 能替你给某个窗格单独派活，也能把某个窗格的上下文提前压缩。你不用在五个 tmux pane 之间来回切、复制粘贴、手动同步进度。

/agents 分屏：窗格不是“另一个聊天框”，是“另一个 Agent 的工位”

把 /agents 想成“给每个 Agent 分配一个工位”，比想成“多标签聊天”更准确。官方 CHANGELOG 对 v0.2.0 的描述非常细，我挑几条关键的翻译成人话：

能力 具体行为
分屏与扇出 一个共享 prompt 同时发给所有选中 Agent；每个窗格有独立滚动、复制、消息操作
会话持久化 每个窗格第一次结束后绑定自己的可恢复 ACP 会话；重启后从 session/load 回放恢复（含模型、推理模式）
模型独立 每个窗格可以单独选模型，/models 只提交给当前聚焦窗格，且跨窗格会话记住上次选择
Worktree 隔离 任何窗格（以及主 Agent 自己）都可以跑在自己的 git worktree 里；拒绝两个 Agent 挤在同一个 checkout
协调方式 主 Agent 用 agents_call（阻塞等报告，或后台挂起）和 agents_compact（提前压缩某窗格上下文）
窗格间纪律 协调工具被从子 Agent 的循环里剥掉——子 Agent 只报告，不互相协调

最后一条最像“管理者设计”：子 Agent 没有 agents_call 这类工具，它们不能自己再去派活。所有跨 Agent 协调必须经过主 Agent。这避免了“三个 Agent 互相甩锅、无限递归派活”的常见多 Agent 灾难。

Worktree 隔离：为什么这是多 Agent 并行的真正门槛

多 Agent 并行写代码，最大的坑不是“它们不会写”，而是“它们互相踩”。同一个 checkout 里，A 刚改了 src/main.rs，B 的 diff 基于旧版本，merge 时就是一场小型车祸。

Cosh 的做法是 opt-in worktree isolation：每个窗格可以绑定一个 git worktree，主 Agent 也能单独跑在隔离 worktree 里，退出时回到共享 checkout。官方明确写了几个约束：

  • 拒绝两个 Agent 跑在同一个 checkout（防止互相覆盖）；
  • 能识别并接管已有 worktree，也能按显式路径解析；
  • 路径带空格会正确加引号；
  • 主 Agent 的隔离带“返回共享 checkout”的退出路径。

这一点，比“分屏”本身更值钱。分屏只是 UI，worktree 才是并发正确性的地基。 没有隔离的多 Agent 并行，本质上是把“单线程改代码”变成“多线程改代码但不加锁”——你只是更快地制造冲突。

接入外部 Agent 靠什么：ACP 协议与注册表

Cosh 能驱动 Claude Code、Codex、Goose，靠的是 ACP（Agent Client Protocol）。CHANGELOG 里把它叫“external ACP agents”，并提到一个合成条目“cosh manager”。注册表内置的 harness 包括：

  • GitHub Copilot CLI
  • Gemini
  • Claude
  • Codex
  • Cline
  • Devin
  • Goose
  • OpenCode
  • Kilo

此外，用户可以在 setup.json 里注册自定义 ACP Agent（单词名 + 启动命令）和自定义 LLM Provider（endpoint + API family，目前 OpenAI-compatible）。注册是 all-or-nothing 校验，坏条目不会拖垮内置 harness。

这里有个工程细节值得注意：v0.2.1 修了一个很典型的兼容性问题——某些 harness（如 goose）广告了 loadSession 但没有 sessionCapabilities.resume，会在每次窗格轮次前把保留的对话当普通 session/update 事件重放，污染时间线。Cosh 的处理是：在会话打开窗口内丢弃重放内容，但保留 UI 框架，让 rehydrate 路径用未过滤的处理器。

这就是“编排层”的真实成本：你对接的每个 Agent 都有自己的会话语义、重启行为、能力广告，协议层面的“看起来兼容”和“实际能恢复”之间，隔着大量这种边角修复。

和 Claude Squad、Agent Orchestrator 有什么本质区别

这三个东西经常被放在一起讨论，但定位其实差很远：

维度 Cosh Claude Squad Agent Orchestrator
核心隐喻 终端里的 Agent 团队工作台 单个 Agent 的并行会话管理器 团队级并行 PR 流水线
并行对象 异构外部 Agent（Claude/Codex/Goose…） 同构 Agent（Claude Code 多实例） 同构 Agent + GitHub Issues
隔离方式 分屏 + git worktree 会话/分支级 git worktree + 独立分支
协调者 主 Agent（人可介入） 人/脚本 编排器（自动 CI/审查/合并）
成熟度 v0.2.2，早期 已有较大用户群 Composio 出品，偏企业
适合场景 个人开发者想同时试多个 Agent 一个人并行处理多个独立任务 团队把 Issue 批量喂给 Agent

Cosh 的差异化在“异构”。Claude Squad 假设你只用 Claude Code，追求的是同一工具多开；Cosh 假设你已经在用 Claude Code、Codex、Goose，但不想维护多套上下文、多套配置、多个终端。它把“选哪个 Agent”从决策问题变成运行时问题——你可以让 Claude 写重构、让 Codex 跑测试、让 Goose 做验证，然后在一个终端里看结果。

但代价也明显：它依赖你已经有这些 Agent 的账号、配置和 CLI。Cosh 不替你解决“我没装 Goose”或“我的 Codex 配额用完了”这类问题。

运行时层：被 README 低估的真正价值

README 主要讲 UI 和 crates，但 CHANGELOG 里最有信息量的部分是运行时修复。我挑几个能反映“Agent 生产化”真实痛点的地方：

1. 自然停机门禁（harness-natural-stop-gate）

Agent 循环有时会“静默半途停机”。官方文档列了三种形态：

  • 只输出 reasoning 流，finish_reason = "stop" 但 answer token 为 0；
  • 完全空响应；
  • 工具调用之间插入的叙述文本（“Now I’ll run the tests.”）后直接停止。

根因是：停机门禁把任何白名单 finish_reason（stop | end_turn | tool_calls）都当成任务完成。但 finish_reason 描述的是响应，不是任务。修复后，停机门禁会结合 TODO 是否还有未完成项、是否已有报告义务等信号判断，而不是只看模型这一轮“说完了”。

2. bash 进程树看门狗

bash_run 有一个 liveness watchdog，采样整个进程树（bash 会派生子进程，所以看树而不是只看 shell）的三个进度信号：新输出、累计 CPU 时间增长、I/O 计数增长。三者都没有持续 120 秒，判定挂死并杀掉。任何单个信号都会重置计数器，所以构建、下载这类长任务不会被误杀。

同时，Unix 下所有 kill 路径改为向整个进程组发 SIGKILL——旧行为只杀 shell，会漏掉“泄漏的 yes >/dev/null 把一个核转到永远”。这类修复，才是 Agent 从“能跑”到“能上线”的分水岭。

3. 上下文压缩与会话持久化

harness/context 模块是 Cosh 的会话唯一权威：所有事件（用户请求、assistant 响应、工具调用、工具结果）进入一条按显示顺序排列的 timeline，build_messages 按需提供发给 provider 的消息列表。三种压缩策略：one-shot LLM compaction、分层 MapReduce、legacy split-and-concatenate。

context-compaction 文档里有一句我很认同的设计原则：

The session JSONL is the only authoritative session history. A checkpoint is an appended derived summary, not a replacement transcript.

翻译：会话 JSONL 是唯一权威历史；checkpoint 是追加的派生摘要，不是替换 transcript。 这避免了“压缩丢信息、回滚没法做”的常见问题。

模块化：五个 crate，各自能独立用

Cosh 不是单体应用，五个 crate 都可以当库用：

Crate 作用 能否独立用
cosh-sdk LLM 连接器（28 provider）、工具调用抽取、hashline 补丁引擎、文件回滚、LSP 客户端、AST 智能 是，无 app 依赖
cosh-tools 所有暴露给 Agent 的工具（fs/bash/find/lsp/computer/web/skills/subagent/plan/question/recall） 是
cosh-tui Ratatui 组件层（markdown/diff 渲染、布局、Solid 风格响应层） 是
cosh-recall 可选 RAG 层（fastembed 本地向量 + LanceDB） 是（embed feature）
cosh-onnx ONNX 决策引擎（DecisionModel trait + Laya 实现） 是（onnx feature）

cosh-sdk 的 README 里有一个细节：Rust 2024 edition（≥ 1.85）；tree-sitter 语法依赖（约 50 个 crate）是主要编译成本；如果只需要 connector 或补丁引擎，编译会更快。这对想二次开发的人很实用。

cosh-tools 里有个设计我特别喜欢：读文件返回 file_hash，写文件必须校验；编辑锚定在 hashline 标签上，每个 target 独立报错；每次写都记录版本用于会话回滚。所有路径在项目 root 设置前一律拒绝，另有写/只读 allow/blocklist 和 Unix 下内核级沙箱（openat + O_NOFOLLOW）。

HN 上大家其实在质疑什么

Show HN 帖子下只有 4 条评论，但每一条都戳在编排层项目的命门上：

Can someone sell me on orchestration using any tool besides the native support something like claude provides to spin up a few agents whenever it deems that necessary?

翻译：Claude 自己就能按需拉起子 Agent，我为什么还要一个外部编排器？

Similarly could use some screenshots before I pull down and consider it. Also no WHY I would use this over established players like those mentioned in the post.

翻译：先给我截图，还有，凭什么不用 Claude Code / Codex 自己？

作者 Zaluski 的回应是：会补 README 里和其他 TUI 编排器的关键差异说明。

这个质疑是对的：编排层的价值，必须建立在“原生多 Agent 支持不够用”的具体场景上。Cosh 目前给出的答案是：异构 Agent 混用、统一终端、worktree 隔离、可复用 crates。但 v0.2.2 的 Stars 只有 13，说明市场还没投票。

我的判断是：它更适合已经同时使用多个 Agent 的重度用户，而不是只用一个 Agent 的普通人。 如果你只用 Claude Code，Cosh 的编排层对你就是“多一层抽象”；如果你同时用 Claude、Codex、Goose 做对比实验，Cosh 的分屏 + worktree 能省掉大量终端切换和手动同步。

常见问题

Q1: Cosh 和 Claude Code 是什么关系？

A: 不是替代关系。Cosh 是编排层，Claude Code 是它通过 ACP 接入的外部 Agent 之一。你可以把 Claude Code、Codex、Goose 同时放进 Cosh 的 /agents 分屏。

Q2: 它支持 macOS 吗？

A: 官方 README 明确写“macOS hasn’t been tested yet”，只标注 Linux 和 Windows 已测试。macOS 用户要谨慎，遇到问题官方让你开 issue。

Q3: 每个 Agent 真的互不干扰吗？

A: 会话和模型是隔离的；worktree 是 opt-in 的隔离机制。官方会拒绝两个 Agent 挤在同一个 checkout。但如果你不开 worktree，它们仍在同一个工作目录里——并发正确性需要你自己负责。

Q4: 它解决“上下文爆炸”问题吗？

A: 有专门设计。harness/context 模块是会话唯一权威，支持三种压缩策略；agents_compact 工具可以让主 Agent 提前压缩某个窗格，不用等 harness 自己到 80% 触发。

Q5: 和 OpenClaw 的多 Agent 架构有什么区别？

A: 两者都做编排，但抽象层不同。OpenClaw 更偏“Agent 运行时 + 插件/技能体系”，Cosh 更偏“终端 TUI 里的异构 Agent 工作台 + worktree 并发”。OpenClaw 的强项是长期运行、插件生态、渠道接入；Cosh 的强项是把多个现成 CLI Agent 塞进一个终端协同。

Q6: 现在能用于生产吗？

A: v0.2.2，迭代很快，但 Stars 13、macOS 未测试、协议兼容层还在修边角。建议先当“实验工具”，别把核心工作流押在它身上。

Q7: 它的 SDK 能单独用吗？

A: 能。cosh-sdk 是纯库，无 app 依赖，包含 28 个 provider 的 LLM 连接器、工具调用抽取、hashline 补丁引擎、文件回滚、LSP 客户端和 AST 智能。Rust ≥ 1.85。

WinGet 官方 MCP Server 上线：让 AI 帮你装软件，到底能信到什么程度

你有没有过这种时刻：让 AI 帮你配环境，它给你一段 winget install XXX，你复制粘贴回车，然后盯着进度条祈祷下载源没挂。如果 AI 能自己把这一步做完，体验会完全不同——微软在 WinGet 1.12 里内置的 MCP Server，就是在做这件事。

TL;DR

  • WinGet 1.12 起内置 MCP Server，一条 winget mcp 就能拿到客户端配置 JSON
  • 目前只开放 find（搜包）和 install（装包）两个工具，后者每次都要人工批准
  • 走的是标准 stdio MCP 协议，VS Code Copilot 与 GitHub Copilot CLI 有官方接入路径
  • 想把安装权交给 Agent，风险不在协议，而在「谁给 Agent 装、装的东西从哪来」
  • 本文结论：值得玩，但别当成无人值守的装机流水线

这事的本质：微软把「包管理器」接进了 MCP 生态

先交代背景。WinGet（Windows Package Manager）是微软自己的命令行包管理器，地位大概相当于 macOS 的 Homebrew、Linux 的 apt，2020 年随 Windows 10 后期版本铺开，Windows 11 直接内置。长期以来它的用法就一句话：winget install Mozilla.Firefox。

变化发生在 WinGet 1.12。根据 microsoft/winget-cli 仓库 Discussion #5868（发布于 2025-11-11）的 v1.12.420 发布说明，这一版的新特性第一条就是：MCP server available; run winget mcp for assistance on configuring your client。同版本还顺手做了 App Installer 迁移到 WinUI 3、清单 schema 升到 v1.12、新增 Font 安装类型等。

也就是说，这不是某个第三方写的桥接小工具，而是微软官方把 WinGet 的核心能力——查包、装包——封装成了符合 MCP（Model Context Protocol）标准的工具服务。MCP 是什么不用展开，你只要知道：它是让 AI 客户端统一发现并调用外部工具的一套开放协议，VS Code、各类 Copilot 都在往上面接。

来自 Microsoft Learn 官方的说明更直白：WinGet MCP Server 把 WinGet 的核心功能暴露给 AI Agent，让它能帮你找包、理解包的详情、协助安装流程。协议链路是：AI Agent 用 MCP 协议查询 WinGet MCP Server → Server 转调对应的 WinGet CLI 命令 → CLI 在仓库里完成搜索或安装 → 结果原路返回。

怎么开起来：三步，比想象中朴素

前置条件（官方文档列得很清楚）：

  • Windows 11，或 Windows 10 版本 1809（build 17763）及以上
  • VS Code v1.104 或更高，并启用 GitHub Copilot 扩展
  • 装了带 MCP 支持的 WinGet
  • 先打开扩展功能开关：winget configure --enable

第一步，找到可执行文件路径。PowerShell 里跑：

winget mcp

它会直接打印出一段 JSON 配置，里面包含 WindowsPackageManagerMCPServer.exe 的完整路径。如果提示 Unrecognized command: 'mcp'，说明你的 WinGet 版本还不支持，去商店更新 App Installer 再试。

第二步，把这段 JSON 填进 VS Code 项目根目录的 .vscode/mcp.json：

{
  "servers": {
    "winget-mcp": {
      "type": "stdio",
      "command": "C:\\Users\\<你的用户名>\\AppData\\Local\\Microsoft\\WindowsApps\\Microsoft.DesktopAppInstaller_8wekyb3d8bbwe\\WindowsPackageManagerMCPServer.exe"
    }
  },
  "inputs": []
}

第三步，打开 Copilot Chat 切到 Agent 模式，在工具列表里确认 winget-mcp 已勾选。GitHub Copilot CLI 那条路更简单：启动 copilot，输入 /mcp add，填路径保存即可，之后它会在你的提示涉及包管理时自动调用。

只有两个工具，这不是偷懒

翻 Microsoft Learn 的 usage 文档，「Available commands」下面干净得让人意外：

工具 作用 关键约束
find 按自然语言意图搜包，翻译成 winget search 你不用手拼参数，Agent 自己构造查询
install 按自然语言确定包 ID、版本、选项，拼成 winget install 每次执行前都必须经过你的批准

官方点名的当前限制有两条：一是 Agent 不保证每个查询都走 WinGet MCP（「specific prompting can encourage its use」）；二是工具面确实只有 find 和 install，升级、卸载、导出清单这些暂时都没开放。

第三方作者 Gijs Reijn 在 2026-11-24 的实操文章里补充了协议层细节：MCP Server 以 stdio 进程启动，注册的工具名是 find-winget-packages 和 install-winget-package，握手用的 protocolVersion 是 2024-11-05。他还给了一个很实用的提醒——想让 Copilot 稳定触发 WinGet 工具，提示词里最好显式带上「using WinGet」「from WinGet」这类关键词，否则它可能直接凭记忆回答，压根不调工具。

让 AI 装软件，爽在哪、险在哪

爽的部分是真实的。以前你面对新机器，要么翻下载站赌哪个链接不是广告，要么背命令。现在可以问「帮我找一款免费的 PDF 阅读器」「装 Node.js 20 LTS」，Agent 把仓库里真实存在的包掏出来，你确认后它执行——下载源、版本号、哈希校验这些脏活它都替你走了。对不想记参数、也不想碰官网到商店这一串跳转的人，这是实打实的减负。

险的部分也得说透。WinGet 仓库不是真空，社区提交的清单里出现过仿冒包、投毒包；本站之前写过《Windows 软件下载站避坑指南》，讲的就是假官网和捆绑安装器这个老问题。MCP 只是把「执行」这一步自动化了，它不会帮你判断这个包该不该信。而 Agent 有个坏习惯：你让它装 Git，它可能顺手把名字相近的另一个包装上。人工批准这道关卡看着像安全网，但它只在 install 这一层——一旦你习惯了无脑点「批准」，这道网就形同虚设。

所以我的判断是：把它当「代查 + 代执行」的助手，别把它当无人值守流水线。 涉及开发机镜像、批量装机、生产环境这类场景，优先用固定版本号的显式清单加脚本，而不是自然语言对话。

和 Scoop、Chocolatey 比，差在哪

Windows 上的命令行包管理一直是三足鼎立，定位差别很大：

维度 WinGet Scoop Chocolatey
出身 微软官方，系统级 社区，用户目录级 社区，系统级
默认安装位置 遵循各安装器，多为系统目录 用户目录，无需 UAC 系统目录
包数量级 官方仓库数千，含大量桌面软件 偏开发者命令行工具 老牌，商业+社区源
MCP 支持 1.12 起官方内置 暂无官方 MCP 暂无官方 MCP
适合谁 想省心装常规软件的人 喜欢绿色、便携、免管理员的开发者 需要企业级集中管理的团队

注意最后一行差距：MCP 支持目前只有 WinGet 有，而且是官方做的。Scoop 在「干净、可移植、好清理」上口碑很好，Chocolatey 在企业场景更成熟，但它们都没接 MCP——想让 AI 帮你操作包管理，WinGet 现在是唯一一条官方通道。这也解释了为什么微软选在这个时间点动手：包管理是 AI 编程助手绕不开的一环，谁先把接口铺好，谁就拿到 Agent 生态的入口。

常见问题

Q1: winget mcp 报错 `Unrecognized command: ‘mcp’，怎么办？

A: 说明你的 WinGet 还是旧版。去 Microsoft Store 更新 App Installer 到 1.12 以上，再跑 winget configure --enable 打开扩展功能，然后重试。第三方实测提到预览通道需要 WinGet 1.12.170-preview 以上，正式版 1.12.420 已包含该功能。

Q2: 只支持 find 和 install，那升级、卸载怎么办？

A: 官方文档明说当前只开放这两个工具，未来版本可能扩充。现在想升级还是得回到 winget upgrade、winget uninstall 这些 CLI 命令，Agent 只能通过 install 帮你装。

Q3: 装包的时候 AI 会不会不打招呼就动手？

A: 不会。按 Microsoft Learn 的说明，Agent 在执行任何安装命令前都会先征得你的批准，Copilot CLI 也是每次搜索或安装请求后询问。但这道防线依赖你每次都看一眼，别养成无脑点批准的习惯。

Q4: 提示词怎么写才能稳定触发 WinGet 工具？

A: 用明确表达包管理意图的说法，比如「Search WinGet for a PDF reader」「Install Node.js 20 LTS from WinGet」。如果 Agent 没自动调用，就在提示里加上「using WinGet」「from WinGet」这类关键词。

Q5: 我的环境是 Windows 10，能用吗？

A: 能，但要求版本 1809（build 17763）或更高，且 VS Code 要 v1.104+。低于这个版本的老机器就别折腾了。

Q6: 它和 Scoop、Chocolatey 冲突吗？

A: 不冲突，它们是独立的包管理器，装出来的东西各自登记在各自的数据库里。但同一个软件被两套管理器装一遍容易互相覆盖 PATH，建议一台机器选定一个主力，另一个只作备用。

Q7: 这功能适合用来给一批新电脑批量装机吗？

A: 不建议走对话路线。批量场景要的是可复现：把包清单和版本号写成显式配置或脚本，一次审核、处处执行。自然语言对话适合单机的探索性安装，不适合规模化交付。

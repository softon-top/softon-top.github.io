装机必备失踪 3 年,Motrix 2.0.0 beta 归来:这次它想让 AI Agent 帮你按下下载键

我第一次装 Motrix 是 2019 年。那时候我刚从 IDM 的授权码轮盘里逃出来,想找一个界面不油腻、不弹广告、又能吃磁力链接和 BT 种子的下载器。Motrix 一装上就是那种"啊,这个就够了"的感觉——干干净净一个仪表盘,一个添加按钮,一个速度曲线,Aria2 老引擎在底下稳稳跑,任务从来不掉链子。

然后它就没了动静。

上一次 Motrix 发正式版本,是 2023 年。此后 GitHub 仓库像被按了暂停键,浏览器扩展慢慢腐烂,底层的 aria2 内核也停在了 2023 的版本号上不动。装机必备变成了装机遗物,大家都以为作者放弃了这个 5.2 万 star 的项目。

社区急得直接开始了自救。有位博士研究生用 AI 把 Motrix 和 Aria2 整个啃了一遍,搞出了架构完全不同的 Motrix Next,用 Tauri 2 + Vue 3 + Pinia 重写外壳,底层换成了自己重构的 Aria2 Next,顺手补上了 ED2K 支持——一个开源项目沉寂到"用户被逼着自己 fork 一版"的地步,基本可以宣判临床死亡了。

结果 8 月 16 日,Motrix 作者 agalwood 突然放出了 2.0.0 Turbo beta。

时隔 3 年,不是补丁,是推倒重来

拿到这个消息我第一反应不是"有什么新功能",是"能更新就是最大的功能"。

但打开 release notes 看完,我发现这不是那种憋了很久终于挤出来的小版本。v2.0.0 Turbo 是把 Motrix 从头到脚重构了一遍。

老的 1.x 是一个纯客户端下载器:一个 Electron 打包的桌面 UI,底下塞一个 aria2 二进制,通过 JSON-RPC 通信,能跨平台但架构相当"直男"。

Turbo 版本的形态完全变了:

  • 全新的桌面应用,支持可自定义仪表盘、深色模式,主要面向本地下载场景
  • 统一的下载核心,桌面端和 Server 共享同一套下载引擎,支持 HTTP、FTP、BitTorrent、磁力链接、任务恢复、Tracker 更新、UPnP/NAT-PMP
  • 独立的 Server 端,提供官方 Docker 镜像,可以直接扔到 NAS 或者小服务器上做常驻下载机
  • 跨设备控制协议 MDXP,让 CLI、浏览器插件、桌面端可以互相通信,支持局域网自动发现和跨网络 device-code 配对
  • 插件市场,把功能扩展从"改代码 fork 一份"变成"装个插件"
  • 命令行工具 @motrix/cli

看到这份清单我有点恍惚。Motrix 团队没有做一个"更好的下载器",他们做了一个**“下载器基础设施”**——你可以在 NAS 上跑一个下载中心,在电脑上开桌面客户端,在浏览器点一下就把任务丢给远程的 Server,在终端里用命令行遥控整个系统,甚至让 AI 帮你按这些按钮。

MDXP 是关键:Motrix 从"软件"变"节点"

那份 release notes 里最不起眼、也最关键的一个词,叫 MDXP——Motrix Device eXchange Protocol,Motrix 自己搞的一套设备互联协议。

以前你想让 Motrix 帮你下东西,只有一种姿势:打开桌面端,复制链接,粘贴,点确认。桌面端就是唯一的入口,别的什么都进不去。

MDXP 直接把这条路拆了。现在 Motrix 变成了一个"节点":

  • 家里 NAS 上跑一个 Motrix Server,永远开机,永远在下载
  • 办公室电脑打开桌面客户端,MDXP 会自动发现 NAS 上的 Server,配对之后就能远程管理它的任务队列
  • 手机浏览器里看到一个磁力链接,通过浏览器扩展直接把任务丢给远程 Server
  • 出门在外网也能通过 device-code 配对连回 NAS

这套设计在 SSH / VPN 玩家眼里可能觉得"不就是远程 API 嘛",但对普通用户,这解决的是一个非常真实的痛点:大文件下载和你人在哪儿这件事,应该解耦。以前想让下载器在 NAS 上跑,你得研究 aria2、qBittorrent、Transmission 各家远程配置,搞 basic auth、开端口、配反代,劝退。Motrix Turbo 相当于把这一堆手工活变成了"打开 App 点连接"。

这也是 Motrix 从桌面下载器,进化成"个人下载云"的转折点。

CLI + Agent Skill:AI 时代的下载器长这样

如果 MDXP 是给人用的遥控器,那 CLI 就是给 AI 用的。

Turbo 版本里我最感兴趣的组件,是这个新出的 @motrix/cli。装法一句话:

npm install -g @motrix/cli@latest

装完之后你有了一套完整的命令行工具:

命令 用途
motrix list [--status] [--limit] [--offset] 列出下载任务
motrix stats 聚合速度与任务计数
motrix open [--timeout] 启动本地桌面 app 并等待其 bridge 就绪
motrix add <url> --save-dir <dir> [--filename] [--header "K: V"] [--connections] [--proxy] 添加 HTTP(S) / FTP 下载
motrix add --magnet <link> --save-dir <dir> [--select 0,2] 添加 magnet 链接
motrix add --torrent <file> --save-dir <dir> 添加 .torrent 文件
motrix pause <id> 暂停任务
motrix resume <id> 恢复任务
motrix remove <id> [--delete-files] 移除任务
motrix watch [--task] [--stats] 以 NDJSON 流式输出进度
motrix pair [--name] 通过 device code 与 bridge 配对
motrix describe 打印 MDXP 工具目录
`motrix skill path install [dir]`
motrix self-update [target] [--dry-run] 通过安装它的包管理器更新 CLI 自身

命令表看着朴素,但注意最后一列几行——motrix skill install、motrix describe、motrix watch——这几个是给 AI Agent 准备的。

关键那一行是 motrix skill install [dir]。它做的事情非常简单:把 Motrix 内置的一份 SKILL.md 复制到目标目录,默认是 ~/.claude/skills/。这份 SKILL.md 就是 Claude Code / OpenClaw 这类 Agent 框架里的 Skill 描述文件,告诉 AI “你现在有一个叫 Motrix 的下载工具,以下是它的命令和用法”。

装完之后,你对着 Claude Code 或者 OpenClaw 说:

  • “帮我下载这个链接到 ~/Downloads/movies/”
  • “把当前所有活跃任务停一下”
  • “看看家里 NAS 上下载得怎么样了”
  • “刚才那个种子选前 3 个文件下载就行,其他跳过”

AI 会调用 motrix add、motrix pause、motrix list、motrix pair 等命令,自己拼参数、自己解析 NDJSON 输出、自己汇报进度。你从一个"复制粘贴链接的操作工",变成了一个"跟 AI 讲需求的甲方"。

**这是我第一次看到一个下载工具官方主动为 AI Agent 铺路。**iPlay、Aria2Fast、qBittorrent 都是 UI 优先思路,人操作 UI,UI 操作引擎。Motrix Turbo 把这条链路反过来:先做 CLI 和协议,再做 UI,让 AI 和人变成"平权"的两种客户端。这个 mental model 的调整,比 UI 上任何一处像素变化都重要。

一个项目两条路:Motrix Next vs Motrix Turbo

聊完官方版,回头看社区的 Motrix Next,现在有点微妙。

Motrix Next 走的是极简 + 现代化 UI 路线:Tauri 2 让安装包从 200M 缩到 20M 出头,内存占用相比 Electron 版本掉了一半以上,UI 做了 Material Design 3 的动效精修,ED2K 也补上了,浏览器扩展体验被大改。它面向的是"我只需要一个漂亮、轻量、本地的下载器,越简单越好"的用户。

Motrix Turbo 走的是平台化 + AI Agent 路线:桌面壳依然是 Electron(相对更重),但配套了 Server、Docker、CLI、插件市场、跨设备协议,是一整套的下载中台。它面向的是"我有 NAS,我有 AI 工作流,我要下载能力可编排"的用户。

两条路其实并不冲突。**Next 是一个更好的 Motrix,Turbo 是 Motrix 之外的一整个生态。**如果你只是想找个界面漂亮的下载器塞进 Windows,Next 更合适;如果你已经在跑 Home Assistant、Jellyfin、AI Agent 那种自建服务,Turbo 才是你要等的东西。

从项目治理角度看,官方回归这件事本身价值巨大。Motrix Next 再好也是社区自救,长期维护有不确定性;官方一旦重新活过来,底下的 aria2 引擎(现在已经升到 1.37.0-motrix.4)、下载协议扩展、跨平台打包这些"苦力活"才有稳定的接盘人。

现在能装吗?

冷静的答案是:能装,但别把它当唯一的下载器用。

从 beta.18 的 release notes 抠几个警告出来,官方自己说得很直白:

  • 这是预发布软件,安装前请备份现有 Motrix 应用数据和已下载文件
  • 从 Motrix v1 数据迁移的路径尚未验证,不要拿你唯一一份 v1 数据来跑 beta
  • 建议在单独的操作系统账户、单独的机器,或者单独的 Docker 数据目录下并行测试
  • Windows 安装包未签名,会触发 SmartScreen 警告,只从 GitHub 官方 prerelease 下载
  • AppImage 和 Snap 在这个 beta 阶段不发布
  • Windows arm64 和所有 32 位平台不提供

我自己的建议方案是这样:

  1. 现有 Motrix 1.x 别动。把它整个安装目录复制一份到备份盘,包括 %APPDATA%/Motrix(Windows)或 ~/Library/Application Support/Motrix(macOS)。
  2. Turbo 装到不同用户 / 单独 macOS profile / 或者干脆用 Docker 镜像 docker.io/motrixapp/motrix-server:2.0.0-beta.18 起一个 Server 玩玩。
  3. CLI 直接装,不影响本地 Motrix 1.x。CLI 内置的 SKILL.md 装到 ~/.claude/skills/ 也是纯只读文件,可以随时删掉。
  4. 重要文件的下载任务不要放 Turbo 跑,断电、断网、崩溃这些边界情况在 beta 里都还没被验证透。

谁该现在关注这件事

  • NAS 玩家:Server + Docker 镜像基本是量身定做,你终于有个能跑在 NAS 上、支持 HTTP/FTP/BT/磁力全协议、有官方长期维护、UI 又不是从 2005 年穿越回来的选择。
  • AI Agent 玩家:Claude Code、OpenClaw、Cline 这类客户端的用户可以直接把 Motrix 挂到工作流里,不用自己写 wrapper 脚本。
  • 开发者:MDXP 协议、插件 SDK、CLI 三样都是可以拿来做集成的入口,官方还在补开发文档,现在切入门槛低。
  • 只想找个下载器的普通用户:等正式版,或者先用 Motrix Next。beta 折腾成本对纯下载场景没有意义。

Motrix 这次沉寂 3 年再回归,选择的方向本身值得一说——没有去追"更快"、“更多协议"这些老下载器的 KPI,而是承认"下载"这件事已经从桌面软件的一个功能,变成了 AI 工作流里的一个能力。CLI 优先、Server 独立、协议开放、Skill 内置,这四条组合起来看,你会发现它已经不是 2019 年那个只想做"漂亮版 aria2"的项目了。

装机必备失踪 3 年,回来发现现在装机的都不是人了,是 Agent。这大概就是 2026 年了。
